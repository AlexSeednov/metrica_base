[English](README.md) | **Русский**

Единая аналитика и крэш-репортинг Яндекса для Flutter-приложений на базе
[пакета application_base](https://github.com/AlexSeednov/application_base)
с [особой архитектурой](https://miro.com/app/board/uXjVNJVBM3o=/?share_link_id=771428578014):
[AppMetrica](https://appmetrica.yandex.ru) на мобильных платформах,
[Яндекс Метрика](https://metrika.yandex.ru) в вебе, один контракт для обеих.

Это аналог [firebase_base](https://github.com/AlexSeednov/firebase_base):
приложение, которое отчитывается в Firebase, подключает тот пакет, а
приложение, которое отчитывается в Яндекс, этот.

Пока в составе:
* [Аналитика](#аналитика) — события использования, идентификатор пользователя,
  ключевые действия
* [Реестр событий](#реестр-событий) — собственное семейство событий
  приложения на общей базе
* [Просмотры экранов](#просмотры-экранов) — наблюдатель роутера, который
  отправляет каждую смену маршрута
* [Крэш-репортинг](#крэш-репортинг) — ошибки, необработанные исключения и
  журнал последних событий
* [Покупки](#покупки) — отчёты E-commerce для приложения со своим
  биллингом
* [Особенности веба](#особенности-веба) — согласие на cookie, блокировщики

* [Документация](#документация) — настройка счётчика, руководство по
  дашбордам и заметки о согласии на cookie

## Поддерживаемые платформы

* Android — AppMetrica SDK
* iOS — AppMetrica SDK
* Веб — счётчик Яндекс Метрики

Сервисы делятся по типу платформы: веб получает счётчик Метрики, всё
остальное AppMetrica. На Linux, macOS и Windows аналитики по факту нет: у
`appmetrica_plugin` там нет реализации. Сервисы AppMetrica регистрируются и
достаются из getIt, но каждый вызов падает, пишется в лог как ошибка и до
отчёта не доходит. Исключений нет, так что приложение там работает, просто
без аналитики.

## Использование

1. Добавьте в `pubspec.yaml` приложения запись вроде этой (и выполните
   `flutter pub get`):

```yaml
  # Not supported: Linux | macOS | Windows
  metrica_base:
    git:
      url: https://github.com/AlexSeednov/metrica_base
      tag_pattern: v{{version}}
    version: 0.0.3
```

2. Подключите injectable-модуль пакета и передайте в `getIt.init` окружение
   платформы. Две реализации разведены по **окружениям** DI: AppMetrica живёт
   в `mobile`, счётчик Метрики в `web`, а `PlatformEnvironment.current`
   выбирает нужное:

```dart
import 'package:metrica_base/core/const/platform_environment.dart';
import 'package:metrica_base/core/service/service_locator_metrica.module.dart';

@InjectableInit(
  externalPackageModulesBefore: [
    ExternalModule(ApplicationBasePackageModule),
    ExternalModule(MetricaBasePackageModule),
  ],
)
Future<void> configureDependencies() =>
    getIt.init(environment: PlatformEnvironment.current);
```

3. На старте дождитесь инициализации DI и запустите аналитику с ключами
   приложения:

```dart
await configureDependencies();

await MetricaBase.prepare(
  const MetricaConfig(
    appMetricaApiKey: '<AppMetrica API key>',   // mobile; null — off
    yandexMetricaCounterId: 12345678,           // web;    null — off
  ),
);
```

Порядок важен. Когда подключены внешние модули пакетов, `getIt.init()`
асинхронный, поэтому его нужно **дождаться**. `MetricaBase.prepare` берёт
сервисы из getIt, поэтому должен выполняться **после** того, как
`getIt.init()` завершился. Сам `prepare` вызывайте **как можно раньше**:
отсчёт сессий идёт именно отсюда, а всё, что запустится позже, уже застанет
готовый репортер.

Ключи обычно зависят от флейвора. Приложение хранит их в собственной
константе и собирает конфиг, как только флейвор известен; сам пакет флейвор
нигде не читает. Остальные поля `MetricaConfig`:

* `sessionTimeoutSeconds` (60) и `maxReportsInDatabaseCount` (10000) —
  буферизация в мобильном SDK. Почему умолчания отличаются от умолчаний
  самого SDK, объясняют doc-комментарии.
* `advIdentifiersTracking`, `locationTracking` — `null` оставляет умолчания
  SDK. Ставьте `false`, если политика конфиденциальности обещает, что
  идентификаторы и геолокация не собираются.
* `webConsent` — шлюз согласия на cookie для веб-счётчика, см.
  [Особенности веба](#особенности-веба).

Сервисов два: `AnalyticsService` и `CrashReportingService`. Это контракты, и
завязывайтесь только на них: реализации — забота пакета, а в тесте
подставляется фейк. Оба синглтоны, которыми владеет getIt. Берите их через
`getIt<T>()` или через конструктор.

## Аналитика

Методы `AnalyticsService`:

* `logEvent(event)` — событие из реестра приложения, см.
  [Реестр событий](#реестр-событий). На мобильных платформах уходит событием
  AppMetrica с параметрами, в вебе целью счётчика. Для каждого события,
  которое важно в вебе, заведите в кабинете Метрики цель с тем же
  идентификатором: `reachGoal` без цели никуда не попадает, см.
  [`docs/metrica_counter.md`](docs/metrica_counter.md).
* `setUser(userId)` — идентификатор пользователя, `String?`. `null`
  сбрасывает его на мобильных платформах. Веб-счётчик сбросить его не может:
  текущий визит уже привязан, а следующий и так останется анонимным.
  Приложение с числовыми идентификаторами конвертирует их прямо при вызове.
* `markKeyAction()` — поднимает флаг профиля `did_key_action`, по которому
  сегментируют аудиторию. Если действие само по себе отдельное событие,
  вместо этого объявите у события `keyActionCounter`.

Аналитика никогда не влияет на бизнес-логику: каждый вызов защищён, а сбой
только попадает в лог.

## Реестр событий

Реестр событий принадлежит приложению. Оно объявляет собственное семейство
поверх `AnalyticsEventBase`, обычно `sealed`. Пакет никогда не видит
фиксированного списка событий, а у двух приложений на одном пакете общая
только форма:

```dart
sealed class AnalyticsEvent extends AnalyticsEventBase {
  const AnalyticsEvent();
}

final class ProjectCreatedAnalyticsEvent extends AnalyticsEvent {
  const ProjectCreatedAnalyticsEvent({required this.source});

  final String source;

  @override
  String get name => 'project_created';

  @override
  Map<String, Object> get parameters => {'source': source};

  /// A key action of the platform: bumps the lifetime counter of the profile
  @override
  String? get keyActionCounter => 'projects_created_total';
}
```

Реализация читает только то, что событие сообщает о себе само:

* `name` и `parameters` — то, что уходит в отчёт;
* `keyActionCounter` — для событий, которые являются ключевыми действиями
  платформы. На мобильных платформах атрибут-счётчик растёт на единицу и
  поднимается флаг `did_key_action`. У веб-счётчика накопительных атрибутов
  нет, поэтому там ставится только флаг.

`sealed` остаётся в приложении намеренно: sealed-класс нельзя расширить из
другой библиотеки, а исчерпывающие `switch` по реестру, если они есть,
принадлежат самому приложению.

## Просмотры экранов

`AnalyticsNavigatorObserver` — это `AutoRouterObserver`, который отправляет
`ScreenViewAnalyticsEvent` при каждой смене маршрута: push, replace, pop,
переключение вкладки и bottom sheet. В отчёт попадают только именованные
маршруты, поэтому анонимные системные окна остаются в стороне. Добавьте его
в наблюдатели роутера:

```dart
navigatorObservers: () => [AnalyticsNavigatorObserver()],
```

На мобильных платформах просмотр — обычное событие с именем `screen_view`.
В вебе он уходит не целью, а **хитом** страницы SPA: именно это даёт Метрике
её стандартные отчёты по содержанию и позволяет разбирать рекламные метки.
Маршрут отправляется как путь страницы даже при hash-стратегии URL, см.
[Особенности веба](#особенности-веба).

## Крэш-репортинг

`CrashReportingService.prepare()` вызывается из `MetricaBase.prepare` и
подключает отправку отчётов к глобальным обработчикам ошибок и к удалённым
приёмникам логгера `application_base`. В итоге всё, что приложение логирует
как ошибку, становится отчётом без единого дополнительного вызова на местах.

На **мобильных платформах** AppMetrica SDK при активации сам перехватывает
нативные крэши и необработанные ошибки Flutter. Сервис добавляет то, до чего
SDK не дотягивается:

* асинхронные ошибки вне зоны Flutter (`PlatformDispatcher.onError`);
* обработанные ошибки из логгера приложения. Они отправляются с явной
  **группой**: без неё AppMetrica склеивает ошибки по стеку, а у всех вызовов
  логгера он один и тот же;
* **журнал** из 25 последних info-сообщений логгера, чтобы в отчёте было
  видно, что делал пользователь. Он заранее хранится в окружении ошибок,
  потому что нативный крэш никогда не проходит через Dart.

В **вебе** крэш-репортинга у Метрики нет, поэтому ошибки уходят служебным
событием `app_error`: без стеков и журнала, но с той же группировкой. Не
больше 30 за визит, чтобы зациклившаяся ошибка не могла заспамить счётчик.

Группировка — одно правило для всех платформ (`ErrorGroupUtility`): первая
строка сообщения, в которой числа заменены на `#`. Так один и тот же сбой с
разными идентификаторами в тексте попадает в одну запись.

`setUser(userId)` привязывает отчёты к пользователю. Это отдельный вызов, не
тот, что в аналитике: в отчёт о нативном крэше идентификатор нужно заложить
заранее.

## Покупки

Для приложения со своим биллингом (платёжный провайдер, а не сторы)
`AnalyticsService` отправляет воронку покупки:

* `reportCheckoutStarted(purchase)` — начало оформления заказа;
* `reportPurchase(purchase)` — событие `purchase_success`, заказ E-commerce
  и, на мобильных платформах, накопительные атрибуты профиля
  `purchases_count_total` / `purchases_amount_total` (по всем покупкам) и
  `purchases_count_paid` / `purchases_amount_paid` (по платным).

Оба метода принимают один и тот же `AnalyticsPurchase`. Объект один, потому
что два шага должны уйти с одинаковым содержимым, иначе воронка не сходится.
Бесплатные приобретения в E-commerce не попадают, потому что нулевые заказы
исказили бы средний чек. Их учитывают только событие и атрибуты.

Покупки через сторы (IAP) пока не поддерживаются: AppMetrica ждёт их как
Revenue с валидацией по чеку, а это отдельная история.

## Особенности веба

**Согласие на cookie.** Счётчик ставит cookie, поэтому там, где закон требует
согласия, скрипт не должен загружаться, пока пользователь его не дал.
Передайте согласие в `MetricaConfig.webConsent`, это `ValueListenable<bool>`.
Счётчик активируется, как только тот сообщит `true`: сразу, если сохранённое
согласие прочитано при запуске, или позже, когда плашку приняли посреди
сессии. Отчёты, отправленные до активации, копятся в очереди (до 100), чтобы
визит не потерял первые события. `null` означает, что шлюза нет и счётчик
загружается при инициализации.

**Блокировщики рекламы.** Они массово отрезают счётчик. Не загрузившийся
скрипт — ожидаемые условия работы, а не ошибка: активация помечается
неудавшейся с info-логом, и с этого момента каждый отчёт молча отбрасывается.

**Адреса страниц.** При URL-стратегии Flutter по умолчанию маршрут живёт в
хэше (`https://host/#/product/1`), а Метрика хэш не разбирает: все просмотры
схлопнулись бы в один адрес сайта. Перед хитом маршрут переносится в путь
(`https://host/product/1`). Поэтому отчёты не зависят от настроек счётчика и
переживут переход на path-стратегию.

**Скрипт счётчика подключается из Dart**, а не из `index.html`: номер
счётчика зависит от флейвора, а `index.html` один на все сборки. На страницу
ничего добавлять не нужно. Если вставить поверх сниппет из кабинета,
поднимется второй счётчик без `defer`, который задвоит первый просмотр в
обход шлюза согласия.

**Сам счётчик**, то есть как его создать, какие настройки важны для Flutter
SPA и какие цели нужны событиям реестра, описан в
[`docs/metrica_counter.md`](docs/metrica_counter.md).
