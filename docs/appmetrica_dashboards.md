# Дашборды AppMetrica

Как устроены два дашборда (в терминах AppMetrica — **воркспейса**) мобильного приложения
на пакете `metrica_base`: «Продукт» — только аналитика, «Стабильность» — только падения и
ошибки. Здесь общая часть: что умеет и чего не умеет кабинет, как заполняется форма
виджета, какие виджеты, воронки, сегменты и оповещения имеют смысл в любом приложении на
пакете, и что снято с кабинета. Собственные события приложения, их виджеты и соответствие
бизнес-метрикам описывает документ проекта — он ссылается сюда и продолжает нумерацию
виджетов своими.

## Что пакет отдаёт в AppMetrica

Сырьё для виджетов, общее для всех приложений на пакете. Собственные события приложения
(`logEvent` по реестру проекта) — сверх этого.

| Что | Имя | Параметры и значения |
|---|---|---|
| Просмотр экрана | событие `screen_view` | `screen_name` — имя маршрута; `type` — `push` / `pop` / `replace` / `tab`; `is_modal`; `previous_screen` |
| Успешная покупка | событие `purchase_success` | `product_id`, `product_name`, `amount`, `currency`, `quantity`, `is_free` |
| E-commerce | начало оформления и покупка | заказ из одного товара: `sku` = `product_id`, название, «Категория товара, ур. 1» = `AnalyticsPurchase.category`, цена, количество, доход; `payload.payment_id`. **Только платные** — бесплатные получения в E-commerce не попадают |
| Счётчики профиля | `purchases_count_total`, `purchases_amount_total`, `purchases_count_paid`, `purchases_amount_paid` | накопительно по всем покупкам и только по платным |
| Признак профиля | `did_key_action` = `true` | ставится покупкой, `markKeyAction()` и любым событием с `keyActionCounter` |
| Счётчики ключевых действий | имя из `keyActionCounter` события | +1 на каждое такое событие; объявляет само приложение |
| Обработанные ошибки | отчёт «Ошибки», группа = первая строка сообщения без чисел | окружение: `user_id`, журнал `log_01 … log_25` |
| Падения и необработанные ошибки | отчёт «Крэши» | перехватывает сам SDK, группировка по стеку |

«Пользователь» в отчётах — устройство; аккаунт (`setUser`) уходит как ProfileID и виден в
отчёте «Профили».

## Решение

- **Два воркспейса в production-приложении AppMetrica.** Dev, stage и production — разные
  приложения в кабинете, воркспейс копируется только внутри своего приложения.
  Настраивается production; для stage при желании повторяется «Стабильность» (там
  ловятся падения до релиза).
- **AI-помощник не умеет создавать воркспейсы, виджеты, воронки и сегменты.** По
  документации он ищет в справке, строит ad-hoc срезы и генерирует ссылки на отчёты с
  нужными фильтрами и группировками. Поэтому настройка — ручная, по этой инструкции.
  Помощник полезен как ускоритель: попросить ссылку на настроенный отчёт и сохранить его
  на воркспейс в два клика (см. «Промпты для AI-помощника»).
- **Внешние дашборды (DataLens) не берутся.** Официальный коннектор отдаёт только 60
  дней, не поддерживает публичный доступ, а параметры событий в его датасете не
  задокументированы. Вернуться к DataLens имеет смысл, только если понадобится одна
  витрина на веб (Яндекс Метрика) и мобильные приложения — тогда через Data Stream API →
  ClickHouse.
- **Конструктор виджетов не видит отчёты о падениях.** Список «Отчёты» в форме виджета
  кончается на «Revenue»: «Крэшей», «Ошибок» и «ANRs» там нет. Зато в каталоге готовых
  виджетов есть «Crash-free», «Crashes» по группам и «Ошибки iOS / Android». Поэтому
  «Продукт» собирается из готовых E-commerce-виджетов и кастомных по «Событиям»,
  «Анализу покупок» и «Аудитории», а «Стабильность» — целиком из готовых виджетов плюс
  **сохранённые отчёты** о падениях, открываемые с воркспейса в один клик. Снятые с
  кабинета списки — в «Справочнике» в конце.
- **Лимиты тарифа «Базовый»:** 20 воркспейсов, до 20 виджетов в каждом, до 100
  сохранённых отчётов. Базовый план ниже — 14 + 7 виджетов и 6 сохранённых отчётов; на
  собственные виджеты приложения в «Продукте» остаётся 6 мест, добавлять сверх — только
  взамен.

## Форма «Создание виджета»

Открывается с воркспейса: **Добавить → Новый виджет**. Поля сверху вниз — в этом же
порядке описана настройка каждого кастомного виджета в таблицах ниже.

| Поле | Что выбирается | Что важно |
|---|---|---|
| Название | свободный текст | называть как в таблицах, чтобы находить по номеру |
| Отчёты | один отчёт-источник из списка с поиском (полный список — в справочнике; отчётов о падениях в нём нет) | после создания сменить нельзя — только новый виджет |
| Тип виджета | График · Таблица · Показатель · Мультивиджет | от типа зависит, какие режимы доступны ниже |
| Показывать в виджете | «Одна метрика» / «Несколько метрик» × «Итого или среднее» / «Автоматически выбранные значения группировок» / «Выбранные вручную значения группировок» | см. таблицу режимов ниже. В режимах «Итого или среднее» поле «Группировки» из формы исчезает |
| Учитывать данные | появляется у отчёта «События»; по умолчанию «Данные: по всем сессиям» | оставить по умолчанию |
| Метрика / Метрики | пикер с поиском, разделы зависят от отчёта; у «Событий» счётчик называется просто **«События»** | |
| Группировки | до 5, порядок — перетаскиванием за ⋮⋮; у «Событий» по умолчанию подставлена «Все параметры, ур. 5» — убрать | порядок = вложенность: сначала «Событие», потом параметр |
| Сегментация | только **сохранённые** сегменты; без них пикер пуст («Нет сохранённых сегментов») | сегменты создаются заранее, шаг 3 |

Режимы «Показывать в виджете» по типам (снято с кабинета):

| Тип | Доступно |
|---|---|
| График | одна метрика в любом режиме; несколько метрик — только «Итого или среднее» (линии по группировке рисуются для одной метрики) |
| Таблица | все шесть режимов — несколько метрик с группировками только здесь |
| Показатель | одна метрика: «Итого или среднее» либо «Выбранные вручную значения группировок» (например, «Пользователи» для одного события) |
| Мультивиджет | ещё не снято |

**Как AppMetrica хранит параметры.** Параметры события — дерево, где ключ и значение —
разные уровни: `screen_name` — уровень 1, имя маршрута — уровень 2. Поэтому группировка
«Все параметры, ур. 1» даёт имена параметров, «ур. 2» — их значения. В таблицах ниже
«Параметр `X`» означает группировку по значениям конкретного ключа: в пикере искать
«Параметр» (в отчёте «События» она есть); если в форме виджета её нет — замена: «Все
параметры, ур. 1» со значением `X`, выбранным вручную, → «Все параметры, ур. 2». У
E-commerce тот же принцип: категория товара из `categoriesPath` — это «Категория товара,
ур. 1».

**Автоматически или вручную.** Параметр, который есть только у одного события
(`screen_name` у `screen_view`, скажем), можно брать в режиме «Автоматически выбранные
значения группировок»: строки других событий в нём просто не появятся. Параметр, общий
для нескольких событий (`product_id`, `amount`, `is_free` есть у `purchase_success`
пакета и у собственных событий воронки покупки, если приложение их шлёт), требует режима
«Выбранные вручную значения группировок» с явным выбором события — иначе виджет сложит
события в одно.

## Воркспейс «Продукт»

Настройки воркспейса (применяются ко всем виджетам): период — последние 30 дней,
валюта — валюта покупок приложения, семплирование — точные данные. Для месячных цифр
период переключается на нужный месяц прямо на воркспейсе.

Обозначения: **готовый** — виджет из каталога (кнопка «Добавить», диалог «Добавить
виджет»); **кастомный** — форма «Создание виджета», настройка записана по её полям: отчёт
и тип · показывать · метрика · группировки · сегмент.

### Аудитория

| # | Виджет | Тип | Настройка |
|---|---|---|---|
| 1 | Аудитория | готовый, «Продукт» | мультивиджет: пользователи, новые, неактивные, вернувшиеся; DAU / WAU / MAU — по детализации периода. Отдельный «Новые пользователи» не нужен — он входит сюда |

## Воркспейс «Стабильность»

Конструктор не даёт собрать виджет по «Крэшам», «Ошибкам» и «ANRs» — таких отчётов нет в
списке источников. Зато готовые виджеты категории «Крэши и ошибки» построены именно на
них, поэтому воркспейс — семь готовых виджетов, а детальные срезы живут **сохранёнными
отчётами**: с воркспейса до них один клик через «Сохранённые отчёты». Период
воркспейса — последние 7 дней, как в отчётах о падениях. Воркспейс одинаков для всех
приложений на пакете: в нём нет ни одного собственного события.

### Виджеты

| # | Виджет | Тип | Что показывает |
|---|---|---|---|
| 1 | Crash-free | готовый, «Крэши и ошибки» | crash-free по операционным системам — тот самый показатель Crashlytics |
| 2 | Crashes | готовый, «Крэши и ошибки» | устройства по группам крэшей — топ групп |
| 3 | Ошибки iOS | готовый, «Крэши и ошибки» | ошибки |
| 4 | Ошибки Android | готовый, «Крэши и ошибки» | ошибки |
| 5 | Версии приложения | готовый, «Технологии» | устройства по версиям — доля аудитории на версии, чтобы читать S2 и S5 в процентах |
| 6 | Операционные системы | готовый, «Технологии» | устройства по ОС — база для чтения виджета 1 |
| 7 | Retention (по версии приложения) | готовый, «Продукт» | релиз, роняющий удержание, виден здесь раньше жалоб |

Заголовки на воркспейсе: «Падения», «Версии».

### Сохранённые отчёты

Создаются в самом отчёте: выставить группировки и метрики → **⋯ → Сохранить как…** с
именем из таблицы. Период — 7 дней. Если у отчёта о падениях в этом меню окажется кнопка
**На workspace**, либо готовые «Crashes» / «Ошибки» редактируются по группировке — часть
таблицы переезжает на воркспейс виджетами (см. «Что проверить в интерфейсе»).

| # | Сохранённый отчёт | Отчёт | Группировка | Метрики |
|---|---|---|---|---|
| S1 | Крэши · топ групп | «Крэши» | «Группа крэша» | «Крэши», «Устройства», «% от всех устройств». Полная версия виджета 2 — с числом крэшей и долей |
| S2 | Крэши · по версиям приложения | «Крэши» | «Версия приложения» | те же |
| S3 | Крэши · по версиям ОС | «Крэши» | «Версия ОС» | «Крэши», «Устройства» |
| S4 | Ошибки · топ групп | «Ошибки» | «Группа ошибки» | «Ошибки», «Устройства», «% от всех устройств». Группа = первая строка сообщения без чисел |
| S5 | Ошибки · по версиям приложения | «Ошибки» | «Версия приложения» | те же |
| S6 | ANR · по версиям приложения | «ANRs» | «Версия приложения» | количество ANR, «Устройства». Только Android |

### Чем это удобнее Crashlytics

- **Crash-free.** Готовый виджет «Crash-free» показывает долю по операционным системам —
  прямой аналог Crashlytics. В самих отчётах о падениях этой метрики нет, там «% от всех
  устройств» — доля устройств с падением от всех, запускавших приложение (crash-free
  devices = 100 − x). Пороги оповещений считаются по «сессиям с крэшами, %».
- **Контекст падения.** У каждого отчёта есть окружение, которое пакет кладёт заранее:
  `user_id` и журнал `log_01 … log_25` — последние записи логгера с временем, в
  хронологическом порядке при сортировке по ключу. Плюс кнопка «Посмотреть события
  сессии»: там видна цепочка `screen_view` до падения — путь пользователя без отдельной
  разметки, как breadcrumbs в Sentry.
- **Группы.** Обработанные ошибки группируются не по стеку, а по идентификатору группы —
  первая строка сообщения без чисел (`ErrorGroupUtility`). Один и тот же сбой с разными
  id в тексте попадает в одну группу; на вебе группировка та же. Необработанные ошибки
  Flutter и нативные падения попадают в «Крэши» (SDK перехватывает их сам),
  группировка — по стеку.
- **Гигиена.** У группы есть статус «Закрыт» (переоткрывается автоматически, если
  воспроизвелась в новой версии) и «Комментарий». Закрывать разобранные группы стоит
  сразу, иначе таблица топ-групп теряет смысл.
- **Символикация** dSYM и mapping заливается сборкой автоматически (Gradle-плагин и фаза
  Xcode). Если стек нативного падения нечитаем — проверить, что загрузка прошла:
  «Настройки → Крэш-логи».

### Оповещения о падениях

Только e-mail, других каналов нет. Путь: **Настройки → Основное → вкладка «Ещё» →
Крэши → «Настройка почтовых уведомлений»**, после сохранения подтвердить адрес по ссылке
из письма. Проверка идёт каждые 10 минут. Раз детальные отчёты о падениях не попадают на
воркспейс, почта — и есть основной канал мониторинга; стартовые пороги:

| Тип | Порог |
|---|---|
| Новые и переоткрытые группы крэшей | включить |
| Сессий с крэшами по приложению | 1 % |
| Сессий с крэшами одной группы | 0,5 % |
| Сессий с ошибками по приложению | 10 % |
| Сессий с ошибками одной группы | 5 % |

Пороги по ошибкам сознательно выше: в отчёт «Ошибки» попадает каждый неудавшийся сетевой
запрос и каждая проверка доступности бэкенда, поэтому в офлайне ошибок много, и это не
инцидент. Через неделю после запуска пороги пересмотреть по фактическому фону.

## Пошаговая инструкция

Нужна роль с правом редактирования у production-приложения; «Только чтение» не сохраняет
сегменты и не редактирует чужие воронки. Всё делается в веб-кабинете AppMetrica,
оценка — полтора-два часа.

### Шаг 1. Воркспейсы

**Workspaces → Добавить workspace** → «<Приложение> · Продукт» → **Применить** без
виджетов; так же «<Приложение> · Стабильность». В настройках воркспейса выставить период
(30 и 7 дней), валюту покупок и точные данные без семплирования.

### Шаг 2. Воронки

**Отчёты → Воронки → Создать воронку.** Для приложения с покупками:

1. «Оформление покупки»: шаг 1 — собственное событие начала оформления, шаг 2 —
   `purchase_success`. «Регистрация событий» — в рамках одной сессии.
2. «Оформление покупки (платные)»: те же шаги, у каждого в блоке «Выбранные события»
   фильтр по ключу `is_free` = `false`.

Остальные воронки — по собственным событиям приложения, в документе проекта.

### Шаг 3. Сохранённые сегменты

Делается **до** виджетов: поле «Сегментация» в форме виджета принимает только
сохранённые сегменты, произвольный там не задать. В отчёте «События»: **Сегмент →
Произвольный сегмент**, затем **Сохранённые сегменты → Сохранить сегмент**.

1. «Ключевое действие»: атрибут профиля `did_key_action` = `true`. Альтернатива через
   события: фильтр «Событие» — события приложения с `keyActionCounter` ИЛИ
   `purchase_success`.
2. «Повторные покупатели»: атрибут профиля `purchases_count_paid` ≥ 2. Если числовое
   условие по счётчику недоступно — фильтр «Событие» `purchase_success` с условием «не
   менее 2 раз» и параметром `is_free` = `false`.
3. «Платящие»: атрибут профиля `purchases_count_paid` ≥ 1 — для сравнения аудитории
   платящих с общей на любом виджете («Сравнить сегменты»).

### Шаг 4. Воркспейс «Продукт»

1. **Добавить** → готовые виджеты 1–4 и 7–11 (для «Воронки» указать воронку из шага 2).
   Между блоками — **Добавить → Заголовок**: «Аудитория», «Навигация», «Покупки»,
   «Ключевые действия» и заголовки блоков приложения.
2. Кастомные виджеты 5, 6, 12–14 и собственные — **Добавить → Новый виджет**, поля формы
   заполнить по колонке «Настройка» сверху вниз: название → отчёт → тип → «Показывать в
   виджете» → метрика → группировки (убрать подставленную «Все параметры, ур. 5»,
   порядок — перетаскиванием) → сегмент → **Создать**. Отчёт после создания не
   меняется — при ошибке проще удалить виджет и завести заново.
   Запасной путь для сложных группировок — из отчёта: открыть «События», кнопка
   «Группировки и метрики», выставить всё в отчёте → **⋯ → Сохранить как…** → **На
   workspace**; настройки виджета заполнятся по отчёту.
3. Расставить виджеты перетаскиванием: до трёх в строке, показатели — в верхней строке
   блока.

### Шаг 5. Воркспейс «Стабильность» и сохранённые отчёты

1. **Добавить** → готовые виджеты 1–7 по таблице: четыре из «Крэшей и ошибок», два из
   «Технологий», «Retention (по версии приложения)» из «Продукта». Заголовки: «Падения»,
   «Версии».
2. Открыть отчёт «Крэши»: выставить группировку и метрики из строки S1 → **⋯ →
   Сохранить как…** → имя «Крэши · топ групп». Если рядом есть кнопка **На workspace** —
   нажать её и повторить для S2–S6 уже как виджеты. Иначе — сохранить S2–S6 отчётами;
   открываются из **Сохранённых отчётов**.

### Шаг 6. Оповещения

Настроить по таблице из раздела «Оповещения о падениях» и подтвердить e-mail.

### Шаг 7. Доступ

**Настройки → Управление доступом.** Публичных ссылок на воркспейсы нет: коллеге нужен
доступ к приложению. «Только чтение» видит все воркспейсы и может делать свои, но не
правит общие — для просмотра этого достаточно.

## Промпты для AI-помощника

## Ограничения

- **Веб не в AppMetrica.** Веб-версия шлёт события в Яндекс Метрику; ошибки там —
  событие `app_error` без стеков. Дашборды выше — только про мобильные приложения. Для
  общей картины числа веба и мобильных складываются вручную, либо позже — DataLens.
- **«Пользователи» в отчётах — это устройства.** Метрика считается по идентификатору
  устройства, а не по аккаунту, хотя пакет передаёт ProfileID. Один человек на двух
  устройствах — два пользователя. Подсчёт по аккаунтам даёт отчёт «Профили»; активную
  аудиторию по аккаунтам брать оттуда или с бэкенда.
- **Данные не мгновенные.** События уходят пачками; часть отчётов формируется с
  задержкой до суток — сверять «сегодня» с бэкендом бессмысленно.
- **Оповещения — только почта,** без Telegram и webhook. Инсайты AppMetrica (левое
  меню) — фиксированный набор автоматических наблюдений без собственных порогов.
- **Дашборд не делится ссылкой.** Только через доступ к приложению.
